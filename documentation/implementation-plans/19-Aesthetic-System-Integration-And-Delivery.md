## Purpose

Make the Impossible Observatory of Living Instruments part of how the portfolio is designed and built, rather than a visual theme applied after feature implementation.

This plan owns the connections between aesthetic intent and the other implementation plans. `18-Art-Direction-And-Aesthetic-Quality.md` owns taste, visual principles, and creative review. Feature plans still own their behavior. This plan defines what each system must provide to art direction, what art direction returns, when that handoff occurs, and how incomplete work remains restartable.

## Core Integration Decision

The Observatory is a shared law of perception, not a shared page template.

- **Portfolio laws** define darkness with causality, concentrated luminous matter, precise diagrams, painterly interference, composed stillness, and depth that changes perception.
- **Surface dialects** translate those laws for Home, the museum, each project, About, AI, blogs, and utility states.
- **Scene compositions** are authored for real content and one dominant visitor action. They are not generated by a universal card layout.
- **Interface utilities** remain legible and consistent but visually subordinate to the scene.
- **Fallbacks** preserve the same hierarchy and meaning without pretending to reproduce every effect.

Shared code should encode behavior, roles, constraints, and quality. It must not force every destination into the same silhouette.

## Six-Layer Integration Model

| Layer | Owner | Inputs | Output to the next layer | Shortcut that is not allowed |
| --- | --- | --- | --- | --- |
| 1. Authored truth | MDX, living state, reviewed graph | Project facts, chronology, evidence, lifecycle, relationships | Stable semantic content and IDs | Inventing visuals around unsupported claims |
| 2. Experience meaning | `EXP`, `PRJ`, `ABT`, `AI` | Destination, depth, discovery, manipulation, current context | What the visitor is doing and learning | Starting from an effect without a semantic cause |
| 3. Art packet | `ART` with the owning feature | Real content, interaction thesis, selected direction | Composition, silhouette, material roles, depth transformation, calm/fallback intent | Styling directly from a wireframe or component inventory |
| 4. Runtime scene | Owning feature package plus `ART-02` foundation | Accepted art packet and behavior contracts | Implemented scene, transitions, semantic visual adapters | Making one global scene component own project identity |
| 5. Utility interface | Shared shell and owning feature | Input, navigation, AI, tour, stimulation, error needs | Quiet controls integrated with the scene | Floating unrelated pills, panels, and widgets |
| 6. Proof and release | `QA`, evidence registry, Mark review | Keyframes, code, tests, stable captures, diagnostics | Accepted creative dimension and safe rollout | Accepting aesthetics from route correctness or one attractive screenshot |

No major visual surface may skip from layer 2 to layer 4. Aesthetic work is incomplete when its art packet exists but its runtime, calm path, fallback, or creative evidence does not.

## Aesthetic Art Packet Contract

Every major surface receives a small, versioned art packet before production styling. It is a planning artifact first; it becomes code only when a runtime consumer needs structured values.

Required fields:

| Field | Purpose |
| --- | --- |
| Emotional thesis | One sentence describing the intended feeling and why it belongs here |
| Visitor truth | The real idea, behavior, or evidence the scene must communicate |
| Focal order | What is perceived first, second, and only after interaction |
| Distant silhouette | The recognizable shape or rhythm before labels and accent color |
| Material roles | What emits, transmits, reflects, absorbs, records, or decays |
| Dominant gesture | The one interaction or transition that the scene is organized around |
| Depth transformations | How Signal, Approach, Handle, Enter, and Understand differ perceptually |
| Semantic inputs | Graph relationships, lifecycle state, evidence, AI context, or discovery state that affect the scene |
| Utility placement | Where navigation, tour, AI, stimulation, and recovery controls belong in the hierarchy |
| Calm profile | The composed sound-off, reduced-motion, and lower-stimulation behavior |
| Fallback composition | The semantic HTML/CSS form when rich rendering or assets fail |
| Performance envelope | Heavy assets, lazy boundary, poster needs, and capability-tier behavior |
| Rejection triggers | Surface-specific ways the implementation could collapse into a generic template |

The packet must use real content and stable destination IDs. Placeholder copy, invented activity, and unreviewed facts cannot receive creative acceptance.

## What Is Shared And What Stays Specific

### Shared Portfolio Laws

These may become tokens, adapters, or primitives after representative scenes prove them:

- Semantic darkness and reveal levels.
- Material roles such as emitter, lens, membrane, paper trace, graphite field, and restrained metal accent.
- Stimulation-aware motion and effect envelopes.
- Transition beats: anticipation, causal response, settlement.
- Diagram line behavior driven by reviewed relationships or product state.
- Utility-control hierarchy and focus visibility.
- Loading, error, and fallback composition rules.
- Capture tooling for stable creative QA frames.

### Surface-Specific Dialects

These must not be flattened into global tokens:

- Focal artifact and distant silhouette.
- Spatial composition and reading path.
- Project metaphor and dominant manipulation.
- Exact material combination and color concentration.
- Typography behavior beyond the site reading baseline.
- Enter/Understand transformation.
- Evidence presentation.

Create a shared primitive only after at least two accepted scenes need the same semantic role. Similar CSS is not enough.

## Semantic Visual Inputs

The aesthetic runtime may respond to reviewed semantic inputs, but it must not turn the knowledge graph into a styling database.

Allowed examples:

- A reviewed `led_to` relationship creates one sight line between two destinations.
- An `evolving` project carries one active trace or unsettled material boundary.
- A `complete` project settles into a composed artifact rather than looking abandoned.
- Selecting an evidence source changes a diagram from latent to inspectable.
- An AI door borrows the silhouette key of its validated destination.

Disallowed examples:

- Storing hex colors, coordinates, animation curves, or component names in relationship records.
- Mapping lifecycle to universal green/yellow/red status colors.
- Rendering every graph edge as a line.
- Allowing generative AI to invent a scene's material or project truth at runtime.

## Depth, Routes, And Composition

Depth is a perceptual transformation inside the approved route model, not a reason to multiply pages.

| Stage | Composition responsibility | Route implication |
| --- | --- | --- |
| Signal | Establish silhouette, disturbance, and a discoverable invitation | Usually transient within the owning route |
| Approach | Resolve identity and central tension while preserving mystery | Stable selection or anchor when useful |
| Handle | Put the dominant project metaphor under the visitor's control | May create bounded safe state |
| Enter | Change scale, framing, material, or spatial rules to feel inside the system | Durable destination when independently useful; often project subdomain |
| Understand | Recompose behavior as evidence, consequence, and connection | Deep-linkable when the explanation is independently useful |

Back, refresh, deep links, and cross-subdomain return must restore a composed safe state rather than replaying an unskippable cinematic transition.

## Delivery Packages And Gates

### `ART-01`: Direction And First Keyframe Selection

- Finish the three Museum Signal alternatives using the same real project set.
- Reject at least one with a written diagnostic.
- Select or revise one with Mark.
- Produce LifeInbox Handle and Understand keyframes inside the selected world.
- Exit with accepted packets and keyframe evidence, not implementation code.

### `ART-02`: Aesthetic Runtime Foundation

- Audit existing tokens, typography, effects, controls, scene boundaries, and capability fallbacks.
- Define semantic material roles and utility hierarchy without creating a universal visual kit.
- Add stimulation/calm/fallback contracts and stable-frame capture support.
- Prototype only the primitives required by the selected museum and LifeInbox packets.
- Exit when the foundation can support `ART-03` without dictating project silhouette.

### `ART-03`: Museum And LifeInbox Remediation

- Implement the selected museum Signal/Approach composition behind an independent flag.
- Implement the selected LifeInbox Handle/Understand transformation while retaining product behavior.
- Integrate AI, tour, sound/stimulation, loading, error, fallback, history, and subdomain return states.
- Run functional regression, performance, diagnostics, stable browser captures, and Mark review.
- Exit by renewing the creative dimension of `QA-02`; retain all previous valid evidence.

### `ART-04`: Remaining Project And Archive Dialects

- Create Dreamlife, Sudoku Together, and smaller-project archive packets from reviewed content and state.
- Prove distinct silhouettes and manipulation languages before `PRJ-05` through `PRJ-07` styling.
- Keep project code in `PRJ-*`; this package owns creative packets and review evidence.
- Exit when downstream project packages have accepted visual inputs and no flagship is a recolored LifeInbox.

### `ART-05`: Home, About, AI, Reading, And Utility Translation

- Translate the selected system into the Home threshold/return state, About chronology, one memory room, global AI states, blogs, and supporting route states.
- Use fewer effects on reading surfaces while preserving material and typographic authorship.
- Resolve utility hierarchy across navigation, tour, stimulation, AI, and recovery.
- Exit when every durable route class has a reviewed packet or an explicitly named later gap.

### `ART-06`: Whole-Portfolio Coherence And Production Maturation

- Review cross-route transitions, material repetition, typography, darkness, motion, asset loading, and visual fatigue.
- Verify each surface feels related but not templated.
- Capture final desktop route/depth matrix in calm and standard stimulation.
- Record remaining mobile and musical work as later rather than silently claiming coverage.
- Exit with whole-portfolio creative acceptance and production evidence.

## Sequencing Rules

1. Complete `ART-01` before new production styling.
2. Implement only the minimum `ART-02` foundation needed by the selected packets.
3. Finish `ART-03` and renew `QA-02` before multiplying the language into other projects.
4. Resolve `LPS-02`/`LPS-03` before `ART-04` uses current-state cues for Dreamlife and Sudoku.
5. Pair each `ART-04` packet with its owning `PRJ-*` package; keep one code package active at a time.
6. Begin `ART-05` with the next active route phase rather than restyling every support surface at once.
7. Run `ART-06` only after representative route classes are implemented.

## Tracking Partial Aesthetic Work

Each capability and work item must state which of these checkpoints exist:

- Thesis and real-content inventory.
- Alternative keyframes.
- Selected packet and rejection rationale.
- Runtime foundation dependencies.
- Representative implementation.
- Calm, fallback, loading, and error states.
- Automated regression and performance verification.
- Stable creative captures and diagnostics.
- Mark review.
- Preview and production rollout.

Do not collapse them into a percentage or the word `polish`. The next exact action should name one observable artifact, such as “render the artifact-led Museum Signal alternative” or “capture the reduced-motion LifeInbox Understand frame,” rather than “continue styling.”

## Completion Criteria

- Every durable route class has an accepted or explicitly pending art packet.
- Museum, LifeInbox, Dreamlife, and Sudoku Together have distinguishable silhouettes and material/interaction dialects.
- The knowledge graph, living state, depth controller, AI, and art direction exchange semantic inputs through owned adapters rather than duplicating truth.
- Utility controls, loading, error, calm, and fallback states are part of scene design.
- Shared primitives encode proven semantic roles without imposing a universal composition.
- Functional evidence remains valid when only creative work is reopened.
- Whole-portfolio review proves one world with meaningful variation, not one visual template repeated across routes.
